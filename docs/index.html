Introduction

Hangar is a self-hosted package registry. It keeps every package your builds need in one place: what you publish, and cached copies of what you download.

Why teams use it#

  • Builds stop depending on the internet. Once a package is cached, a public registry that is down no longer breaks CI: proxy repositories keep serving what they have.
  • One registry for eleven formats. Docker/OCI, npm, Maven, PyPI, NuGet, Go modules, Helm, Cargo, APT, RPM and raw files share one sign-in, one set of roles and one audit log.
  • You see what is risky. Packages are checked against OSV advisories and container images with Trivy. The fix plan shows what to upgrade first, and a repository can quarantine versions with critical findings.
  • It is small. One Go binary with the web UI built in, PostgreSQL for metadata, and package files on a filesystem or in S3. No JVM.

Where to go next#

  • Getting started: From nothing to a working repository, a token and a first upload.
  • Install: The install script (Docker Compose), Helm on Kubernetes, or the binary with systemd.
  • Core concepts: Hosted, proxy and group repositories, URLs and credentials.
  • Configuration: hangar.yaml, HANGAR_* variables and secret files.

Find your way around the docs#

  • Using the UI: Every page of the web UI, with screenshots from the live demo.
  • Package formats: Client set-up and publishing for Docker, npm, Maven, PyPI, NuGet, Go, Helm, Cargo, APT, RPM and raw.
  • Move to Hangar: Import packages from another registry and pre-warm the proxies.
  • Operations: Security hardening, monitoring, alert runbooks and performance.
