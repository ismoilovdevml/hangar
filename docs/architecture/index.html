Hangar — architecture

Runtime topology#

text
                  ┌──────────── clients ─────────────┐
                  docker  npm  mvn  pip  go  helm  CI
                              │ HTTPS
                     ┌────────▼────────┐   (L7 load balancer, sticky not required)
                     │  hangar node ×N │  single Go binary: format handlers, API, UI, jobs
                     └───┬────┬────┬───┘
         PostgreSQL ◄────┘    │    └────► S3 / MinIO / FS  (blobs, content-addressed)
         (metadata, audit,    │
          job queue, events   │
          via LISTEN/NOTIFY)  │
        Trivy server + scan adapter (optional) · OSV advisories · OIDC/LDAP

  • Image scanning: Hangar asks the scan adapter (cmd/hangar-scanner) to scan an image by digest; the adapter runs the Trivy client against the Trivy server and pulls the image back from Hangar's /v2/ with a short-lived, pull-only registry token for that repository (vulnerabilities.md).

  • Nodes are stateless. They keep small in-memory caches (repository lookups, authorization decisions, generated metadata) that events invalidate. Events travel through PostgreSQL LISTEN/NOTIFY; a node whose listener connection was lost drops its caches when it is back. Background work is a jobs table claimed with FOR UPDATE SKIP LOCKED under a lease the running node renews (ADR 0011). A per-node on-disk blob cache and edge replication are planned (roadmap).

  • Leader (via PostgreSQL advisory lock) starts scheduled task runs (cron schedules in tasks); any node executes runs, heart-beating progress, and takes over runs whose node went silent (resuming from checkpoints).

  • Single-node mode: filesystem blobs and one PostgreSQL, nothing else — docker compose up works.

Request path (download)#

  1. Router matches format mount (/v2/ for OCI, /repository/<repo>/... for others, plus vanity hosts like cr.acme.io).
  2. Auth: bearer/basic/token → principal; anonymous if repo allows.
  3. RBAC check repo:<name>:read.
  4. Format handler resolves path → component/asset (group: walk members in order; proxy: cache lookup → upstream fetch on miss with singleflight).
  5. Quarantine check → 403 with explanation body.
  6. Stream blob from the blob store; record download (batched, async) for "last downloaded" and stats.

Upload path#

Handler validates format rules → streams to temp blob while hashing → dedup by sha256 → transaction: component/asset rows, write policy check → emits component.published → scanner job, live feed (SSE). Search reads PostgreSQL directly; replication is planned.

Core interfaces (Go, internal/core)#

go
type BlobStore interface {
    Put(ctx context.Context, r io.Reader) (Digest, int64, error) // streams, hashes, dedups
    Get(ctx context.Context, d Digest) (io.ReadSeekCloser, error)
    Stat(ctx context.Context, d Digest) (BlobInfo, error)
    Delete(ctx context.Context, d Digest) error // only by GC/compaction
}

type Format interface {
    Name() string                          // "docker", "npm", ...
    Mount(r chi.Router, deps Deps)         // registers protocol routes
    Validate(repo *Repository) error       // format-specific config checks
    Coordinates(asset *Asset) Coordinates  // for UI/search
}

type Upstream interface { // proxy repos
    Fetch(ctx context.Context, req UpstreamRequest) (*UpstreamResponse, error) // path, method, headers, conditional
}

The full set, with doc comments, is in internal/core/interfaces.go: BlobStore, BlobStores, Format (+ optional RootMounter), Upstream/Upstreams, HTTPClientFactory, RepositoryService, ComponentService, Authenticator, TokenIssuer, AuthZ, EventBus, JobQueue, AuditLog, and the Deps struct every format receives. In-memory fakes for all of them live in internal/core/coretest. Decisions behind them: docs/adr/.

Routing#

Path Served by
/healthz, /readyz, /metrics operations (liveness; DB + blob store + event listener readiness; Prometheus)
/api/v1/... REST API (api/openapi.yaml)
/repository/{repo}/... format handlers; the dispatcher resolves the repository first
/v2/... OCI (docker format, root mount)
anything else web UI (SPA, embedded)

Corporate networks and reverse proxies#

  • Outbound: every proxy repository reaches its remote through one HTTP client factory. Server-wide http.proxy (http/https/socks5, credentials from env), http.no_proxy, HTTP_PROXY/HTTPS_PROXY/NO_PROXY (default on), http.ca_file, timeouts and pool limits; each remote may override proxy (inherit | none | URL), ca_bundle, insecure_skip_verify and timeouts. Upstream credentials (basic, bearer, named header) are sent only to the remote's own host, never to redirect targets.
  • Inbound: server.base_url is the only source of generated absolute URLs (npm tarballs, OCI token realm, Maven/PyPI links). X-Forwarded-For/Proto/Host are honoured only from server.trusted_proxies. Docker repositories can get a connector: a dedicated host name (cr.example.com) or port.
  • See docs/adr/0008-outbound-http-and-reverse-proxies.md.

API#

  • GET/POST /api/v1/... JSON REST for UI and automation, described in api/openapi.yaml. Resources: repositories, blob-stores, components, assets, search, findings, waivers, cleanup-policies (+ /preview, /{name}/run, /{name}/stop, /{name}/runs), tasks (+ /{id}/run, /{id}/stop, /{id}/runs), users, roles, tokens, audit, nodes, system/status, metrics/overview. Operations marked x-status: planned (replication targets, SBOM, dependents, moving repositories between blob stores) answer 501 until they are implemented.
  • GET /api/v1/events — Server-Sent Events: publishes, quarantines, task progress.
  • Config as code: hangar apply -f / hangar diff / hangar export manage repositories, blob stores, cleanup policies, roles and outbound proxies from YAML over the REST API; ownership for --prune is kept in resource labels (/resource-labels). See guides/config-as-code.md. A Terraform provider does not exist yet.
  • Health: /healthz (liveness), /readyz (DB, blob store, event listener connected), /metrics.

Security#

  • TLS everywhere; HSTS on UI.
  • Passwords argon2id; tokens stored as SHA-256 hashes, prefix hgr_ for secret scanners.
  • CSRF protection for cookie sessions; tokens for CLI/CI.
  • Rate limiting per client address; lockout on failed logins.
  • Proxy SSRF guard: loopback, private, link-local and other internal ranges are refused unless listed in http.allow_private_networks (security).
  • Cosign signatures are stored and served; verifying them by policy is planned.

Integrations (no hard dependency)#

  • CI systems (GitLab CI, Gitea Actions, GitHub Actions, Jenkins, Drone) authenticate with service-account tokens; docs show snippets for each.
  • Planned: OIDC token exchange so CI jobs use their own JWT (GitLab id_tokens, GitHub OIDC) instead of long-lived secrets.
  • Planned: webhooks on events (Slack/Teams via webhook). Today, follow GET /api/v1/events (SSE) or the audit log.
