Container image#

The examples use ghcr.io/ismoilovdevml/hangar:<version>. Until release images are published there, build the image from a release tag and push it to a registry your hosts can pull from, then set HANGAR_IMAGE (compose) or image.repository/image.tag (Helm):

shell
git checkout <version>
make docker IMAGE=registry.internal.example/hangar:<version>
docker push registry.internal.example/hangar:<version>

The build is reproducible: the same commit, VERSION, COMMIT and SOURCE_DATE_EPOCH (all set by make docker) produce identical binaries. Multi-architecture images: docker buildx build --platform linux/amd64,linux/arm64 --build-arg VERSION=... --push -t <image> ..

Configuration in one paragraph#

Hangar reads hangar.yaml (--config or HANGAR_CONFIG) and HANGAR_* environment variables, which win over the file. Every key, its default and its environment variable is documented in hangar.example.yaml. Unknown keys stop the server at start. Secrets belong in the environment or in files in secrets_dir (one file per setting, named after its path: security.secret_key; the compose installer uses this, and it works with Kubernetes secret volumes), never in the file: HANGAR_DATABASE_URL, HANGAR_SECRET_KEY, HANGAR_DOCKER_TOKEN_KEY, HANGAR_STORAGE_S3_SECRET_ACCESS_KEY, HANGAR_HTTP_PROXY_PASSWORD, HANGAR_BOOTSTRAP_ADMIN_PASSWORD.

The settings every production install sets:

Setting Why
server.base_url The public URL. Every link Hangar generates (npm tarballs, the Docker token realm) uses it.
server.trusted_proxies The reverse proxy's address. Without it every client appears to come from the proxy, and all of them share one rate-limit bucket.
HANGAR_SECRET_KEY Encrypts credentials stored in the database. Back it up with the database.
HANGAR_DOCKER_TOKEN_KEY Signs registry tokens. Must be identical on every node and stable across restarts.
database.url PostgreSQL 16 or newer.
storage.* Where blobs live: S3 or a filesystem path.
