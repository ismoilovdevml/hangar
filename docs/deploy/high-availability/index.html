Install and run

High availability

Hangar nodes are stateless: any node serves any request, and no sticky sessions are needed. Availability comes from running two or more nodes on shared, highly available dependencies.

text
              load balancer / ingress  (health check: /readyz)
               |            |            |
           hangar-1     hangar-2     hangar-3        same config and keys
               \            |            /
            PostgreSQL (HA)      S3 / shared FS

PostgreSQL also carries the events between nodes (LISTEN/NOTIFY) and the job queue (the jobs table); there is no other stateful service (ADR 0011).

What each node needs#

Shared Requirement
PostgreSQL One database for all nodes, made highly available by the platform: a managed service, Patroni, CloudNativePG. Connections: nodes x (database.max_conns + 17) (16 for locks, 1 for the event listener), for example 3 nodes with the default max_conns of 20 need 111, plus your other clients, below max_connections. Session-mode connections: LISTEN and advisory locks do not work through PgBouncer in transaction pooling mode (see PgBouncer).
Blob store storage.kind: s3 (recommended) or one filesystem mounted at the same path on every node (NFS, CephFS, a ReadWriteMany volume).
Node address Each node publishes the URL the others reach it at to read its System logs (POST /internal/v1/system/logs, signed with the shared secret key): server.node_url, by default the local address it reaches the database from with the port of server.addr. Set it when that address is not reachable from the other nodes (a database behind a local proxy or sidecar, NAT). The Helm chart sets HANGAR_SERVER_NODE_URL=http://$(POD_IP):8080 on every pod and its NetworkPolicy allows pod-to-pod traffic on that port. Elsewhere, open the port between the nodes in firewalls and security groups.
HANGAR_SECRET_KEY Identical on every node; otherwise a node cannot read credentials another node stored.
HANGAR_DOCKER_TOKEN_KEY Identical on every node; otherwise a registry token or an upload session started on one node is rejected by the next.
Configuration Identical hangar.yaml (the Helm chart renders one ConfigMap).

How the cluster behaves#

  • Requests: every request is independent. Docker chunked uploads carry their state in signed upload URLs, so consecutive chunks may hit different nodes. Sessions are stored in PostgreSQL.
  • Background jobs: every node runs a scheduler, and one is the leader (PostgreSQL advisory lock). The leader enqueues the scheduled task runs (blob GC, audit partitions, cleanup, token purge); any node executes them from the job queue in PostgreSQL. A job is held under a lease its node renews every few minutes; when a node dies, its job runs again elsewhere once the lease (10 minutes) expires. When the leader dies, its lock is released and another node takes over within seconds. APT and RPM metadata and npm package state are regenerated by one coalesced job per repository (or package), on one node, about 2 s after the last change.
  • Caches: repository lookups, authorization decisions and generated metadata are cached per node and invalidated through events (PostgreSQL LISTEN/NOTIFY). A node whose listener connection drops misses events while it is down; when it reconnects it drops all its caches, so stale answers last at most as long as the disconnect.
  • Shutdown: on SIGTERM a node fails /readyz at once, keeps serving new requests for server.drain_delay (default 0) so a load balancer that polls /readyz takes it out of rotation, then stops listening and gives in-flight requests server.shutdown_timeout to finish. See Draining nodes.
  • Migrations: hangar migrate up and migrate_on_start hold a PostgreSQL advisory lock while they run. Nodes that start together wait for the one that migrates and then start on the new schema; a node without migrate_on_start waits too instead of failing on a half-migrated schema.
  • Readiness: /readyz fails when the node cannot reach PostgreSQL or the blob store, or its event listener connection is down. A database outage makes all nodes unready at once; the load balancer then answers 503 until it returns.

PgBouncer#

Each node keeps one PostgreSQL session open for as long as it runs, the event listener (application_name = hangar-listener, LISTEN), and takes session-level advisory locks for the scheduler leader and migrations. Neither works through PgBouncer in transaction pooling mode: the listener never receives events, /readyz fails with eventbus, and locks are lost between statements. Either connect Hangar straight to PostgreSQL, or give its database pool_mode = session with a pool of at least nodes x (database.max_conns + 17) server connections.

Job queue#

Jobs are rows of the jobs table, as durable as the database. Inspect them with SQL:

sql
SELECT type, state, count(*) FROM jobs GROUP BY 1, 2;        -- queued, running, done, dead
SELECT id, type, attempts, last_error, finished_at FROM jobs WHERE state = 'dead';

A dead job failed 5 attempts and is kept for 7 days. To run one again: UPDATE jobs SET state = 'queued', attempts = 0, run_at = now() WHERE id = '...'.

Draining nodes#

Stopping a node without dropping requests needs the load balancer to stop sending it traffic before its listener closes, and the service manager to wait for in-flight uploads:

Setting Meaning
server.drain_delay (0s to 5m, default 0s) After SIGTERM, /readyz answers 503 while the node keeps serving new requests (with Connection: close) for this long. Set it to the time your load balancer needs to notice: health check interval x unhealthy threshold, plus one interval.
server.shutdown_timeout (1s to 24h, default 30s) After the drain delay, the listener closes and in-flight requests get this long to finish; then they are cut off.
Service manager timeout Must exceed drain_delay + shutdown_timeout: systemd TimeoutStopSec, Docker stop_grace_period, Kubernetes terminationGracePeriodSeconds.

In Kubernetes, endpoints are removed when the pod starts terminating, independent of readiness. The chart's lifecycle.preStopSleepSeconds (5) delays SIGTERM until kube-proxy and ingress controllers have caught up, so drain_delay can stay 0. Keep

text
terminationGracePeriodSeconds > preStopSleepSeconds + drain_delay + shutdown_timeout

(chart defaults: 60 > 5 + 0 + 30). Set config.server.drain_delay instead of the sleep on clusters older than 1.30 (no sleep pre-stop action), and in addition to it when a load balancer outside the cluster health-checks the pods directly (for example drain_delay: 15s for a 5 s check interval and a threshold of 2).

Failure scenarios#

Observed on a test cluster (Helm chart, 2 Hangar replicas, MinIO, PostgreSQL; v0.1.x, before the move from NATS to PostgreSQL):

Failure Effect
Registry token issued by one replica, used on the other Accepted (shared HANGAR_DOCKER_TOKEN_KEY).
helm upgrade with a configuration change Migration Job ran, pods were replaced one at a time, generated keys stayed the same, previously uploaded artifacts and images were served by the new pods.

Covered by the integration tests of v0.2.0 (internal/events): a job whose node died is reclaimed once its lease expires; a job that runs for longer than the lease keeps it through heartbeats; a node whose listener connection is terminated reconnects and drops its caches.

Known limits#

  • Event delivery between nodes is best effort: an event published while a node's listener is reconnecting does not reach it, and the node drops its caches when it is back. Durable work never depends on an event reaching another node: it is queued as a job by the publishing node.
  • Rolling upgrade from v0.1.x: v0.1 nodes use NATS, v0.2 nodes PostgreSQL; they do not share events or jobs. Upgrade all nodes together.
  • Migration lock: the advisory lock needs a session-level connection. Run hangar migrate up and nodes with migrate_on_start directly against PostgreSQL or through a session-pooling proxy, not PgBouncer in transaction pooling mode. A node waiting for the lock waits as long as the migration takes.
  • Node list: /api/v1/system/status reports nodes_up/nodes_total from the node heartbeats in PostgreSQL (every 15 s); a node that stopped is counted as down after 45 s and forgotten after an hour.
  • Filesystem blobs on NFS: every write is fsynced; NFS latency bounds publish throughput. Prefer S3 for several nodes.

Cluster-wide and per-node state#

Most state lives in PostgreSQL and the blob store and is the same on every node. A few protections keep counters, and whether those counters must be shared depends on what they protect:

State Scope Why
Sign-in lockout (auth.lockout: failures per username and address, lock duration, slow-down) Cluster (PostgreSQL login_failures) Security control: an attacker spreading guesses over nodes must hit the same counter.
Login rate limit (auth.login_rate, per client address) Cluster (PostgreSQL rate_limit_buckets) Security control against password guessing and spraying. Two nodes allow what one allows, not twice as much. One statement per sign-in attempt.
Failed-authentication limit (security.rate_limit.failed_auth, per client address) Cluster (PostgreSQL rate_limit_buckets) Security control against token and password guessing on the API and package endpoints. Only failed attempts (401, 423) write to the database; the check on each request is answered from the node's memory, so a node learns that a client's budget is spent at that client's next failure on it. A client spreading guesses over N nodes therefore gets the budget once plus at most one attempt per node, not N budgets.
API rate limit (security.rate_limit.api, per client address) Per node Load shedding, not a security control: it runs on every API request, where a database write each time would cost more than it protects. With N nodes a client can send up to N times the configured rate; lower the setting accordingly if that matters, or limit at the load balancer.
Upstream circuit breaker and health (proxy repositories) Per node Each node observes its own connections to the remote, which may differ (network path, DNS, egress proxy). A node opens its breaker after its own consecutive failures; the others keep trying until they see failures too. The System status screen shows each node's view.
Upstream 429 throttle (Retry-After from a remote) Per node A remote that rate-limits one node usually limits by source address, which differs per node. Every node backs off when it is told to.
Live events stream (SSE, Last-Event-ID resume) Per node The replay buffer of the last 256 events is in the node's memory. A browser that reconnects to another node (no sticky sessions) sends a Last-Event-ID that node never saw, gets no replay, and misses the events published while it was disconnected; screens show them on their next refresh. Live updates are a convenience, not a record: the audit log and the API are authoritative.

When PostgreSQL cannot be reached, the shared limits fall back to a bucket in the node's memory with the same settings and log rate limit: shared bucket unavailable, limiting on this node only; sign-in needs the database anyway, so this only matters for its brief outages. Buckets that are full again are deleted by every node's hourly purge.

Multiple sites#

Run one Hangar cluster per site against that site's database and blob store. Replication between sites is on the roadmap (M6). Until then, use the database's and the object store's own replication for disaster recovery, and keep HANGAR_SECRET_KEY and HANGAR_DOCKER_TOKEN_KEY identical at the DR site.
