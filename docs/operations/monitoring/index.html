Monitoring Hangar

Hangar exposes Prometheus metrics, writes structured JSON logs and exports OpenTelemetry traces. This page is the reference for all three and for the dashboards and alerts shipped in deploy/observability/. Alert runbooks are in runbooks.md.

Quick start#

  1. Metrics are served at /metrics on every node (metrics.enabled, metrics.path). Scrape each node with a job named hangar; see deploy/observability/prometheus/prometheus.example.yml. By default /metrics has no authentication: keep it on an internal network, block it at the reverse proxy, or protect it (see Protecting /metrics).
  2. Alerts: load deploy/observability/prometheus/hangar-alerts.yml as a rule file. Check and unit-test them with promtool check rules hangar-alerts.yml and promtool test rules hangar-alerts.test.yml.
  3. Dashboards: import the JSON files in deploy/observability/grafana/ (Dashboards → New → Import) and pick your Prometheus data source. They share the hangar tag and link to each other; the Node variable filters by instance.
  4. Traces: set observability.tracing.enabled: true and observability.tracing.endpoint to an OTLP/HTTP collector (see below).
  5. Logs: ship the process's stderr (JSON lines) to your log system and index request_id and trace_id.

Setting Env Default Meaning

metrics.path HANGAR_METRICS_PATH /metrics Endpoint path.
metrics.auth HANGAR_METRICS_AUTH none none, bearer or basic; see Protecting /metrics.

metrics.bearer_token_file HANGAR_METRICS_BEARER_TOKEN_FILE File holding the token instead (read on start; trailing line breaks dropped).
metrics.username HANGAR_METRICS_USERNAME User name for auth: basic.

metrics.password_file HANGAR_METRICS_PASSWORD_FILE File holding the password instead (read on start).
metrics.allowed_cidrs HANGAR_METRICS_ALLOWED_CIDRS Client networks (CIDRs or IPs, comma-separated in the variable) allowed to scrape; empty allows any. Combines with metrics.auth.
log.level HANGAR_LOG_LEVEL info debug also logs probe and scrape requests.
log.format HANGAR_LOG_FORMAT json json or text.
log.buffer_size HANGAR_LOG_BUFFER_SIZE 5000 Recent records each node keeps in memory for the System logs screen, 100 to 100000 (about 1 KiB each).
server.node_id HANGAR_SERVER_NODE_ID host name Name of the node on the System status and System logs screens. Must be unique per node; set it when host names change on every deploy (containers).
observability.access_log.sample_ratio HANGAR_OBSERVABILITY_ACCESS_LOG_SAMPLE_RATIO 1 Share of requests written to the access log, 0 to 1. Server errors (5xx) are always logged. Metrics and traces are not sampled by it.
observability.tracing.enabled HANGAR_OBSERVABILITY_TRACING_ENABLED false Export traces.
observability.tracing.endpoint HANGAR_OBSERVABILITY_TRACING_ENDPOINT OTLP/HTTP collector URL, e.g. http://otel-collector:4318. Without a path /v1/traces is used; https:// uses TLS with the system roots.
observability.tracing.sample_ratio HANGAR_OBSERVABILITY_TRACING_SAMPLE_RATIO 0.1 Share of new traces recorded, 0 to 1. Requests carrying a sampled W3C traceparent header are always recorded (parent-based sampling).
observability.tracing.service_name HANGAR_OBSERVABILITY_TRACING_SERVICE_NAME hangar service.name of every span.

Collector authentication headers come from the standard OpenTelemetry variables OTEL_EXPORTER_OTLP_HEADERS or OTEL_EXPORTER_OTLP_TRACES_HEADERS (e.g. authorization=Bearer …). If the collector is unreachable, export errors are logged at most once a minute and requests are not affected.

Protecting /metrics#

The endpoint exposes no secrets, but it does reveal repository names, request rates and the build. Pick one of:

metrics.auth Prometheus sends Wrong or missing credentials
none (default) nothing (open)
bearer Authorization: Bearer <metrics.bearer_token> 401, WWW-Authenticate: Bearer realm="metrics"
basic HTTP basic with metrics.username / metrics.password 401, WWW-Authenticate: Basic realm="metrics"

metrics.allowed_cidrs works with any mode: requests from other client addresses get 403 before credentials are checked. The client address is the TCP peer, or the X-Forwarded-For client when the peer is listed in server.trusted_proxies, the same address used for rate limits and the audit log. Tokens and passwords are compared in constant time, and wrong ones count towards the per-IP failed authentication limit (security.rate_limit.failed_auth). The token and password (and their files) are read on start: restart the nodes after rotating them; scrapes answer 401 until Prometheus has the new value too.

A new installation made with deploy/install.sh uses bearer: the installer writes the token to <data>/secrets/metrics.bearer_token (mode 600) and config/hangar.yaml sets metrics.auth: bearer; copy the token to Prometheus. Installations upgraded by the installer keep their config/hangar.yaml, so an open endpoint stays open. A server that serves /metrics with metrics.auth: none and no metrics.allowed_cidrs logs a warning on every start. To protect an existing installation, write a token to secrets/metrics.bearer_token (owner 65532, mode 600), add auth: bearer under metrics: in config/hangar.yaml and restart.

Generate a token with openssl rand -hex 32. Prometheus configurations for each mode (the job name must contain hangar, which the HangarDown alert selects; the Helm chart's ServiceMonitor names it after the release's Service):

yaml
# metrics.auth: none, metrics.allowed_cidrs: [10.0.5.0/24] (the Prometheus subnet)
- job_name: hangar
  static_configs:
    - targets: [hangar-1.internal:8080, hangar-2.internal:8080]

# metrics.auth: bearer
- job_name: hangar
  authorization:
    type: Bearer
    credentials_file: /etc/prometheus/secrets/hangar-metrics-token
  static_configs:
    - targets: [hangar-1.internal:8080, hangar-2.internal:8080]

# metrics.auth: basic
- job_name: hangar
  basic_auth:
    username: prometheus
    password_file: /etc/prometheus/secrets/hangar-metrics-password
  static_configs:
    - targets: [hangar-1.internal:8080, hangar-2.internal:8080]

Behind TLS add scheme: https. With the Helm chart set metrics.auth.mode and metrics.auth.existingSecret (keys metrics-token, or metrics-username and metrics-password); the chart passes the secret to the pods and, with metrics.serviceMonitor.enabled, adds the matching authorization or basicAuth to the ServiceMonitor:

shell
kubectl -n hangar create secret generic hangar-metrics \
  --from-literal=metrics-token="$(openssl rand -hex 32)"
helm upgrade hangar oci://ghcr.io/ismoilovdevml/charts/hangar --version <installed version> \
  -n hangar --reuse-values \
  --set metrics.auth.mode=bearer --set metrics.auth.existingSecret=hangar-metrics

Check a node with curl -H "Authorization: Bearer $TOKEN" http://hangar-1.internal:8080/metrics | head; without the header it answers 401.

Metrics#

All Hangar metrics start with hangar_. The Go runtime (go_*) and process (process_*) collectors are also exported. Every value is per node: aggregate across instances in queries.

Cardinality#

Labels never carry user-controlled values:

  • HTTP metrics use the chi route pattern (/repository/{repo}/*, /api/v1/components/{id}), never the request path; requests no route matched are route="unmatched".
  • method is one of the standard HTTP methods or OTHER; code is the status code or other outside 100–599.
  • Repository names appear in hangar_upstream_state (one series per proxy repository and state, capped at 512 repositories), in the per-repository proxy metrics (those with a repository label) and in hangar_routing_blocked_total; store names appear only in the blob store usage gauges (capped at 64 stores). Repositories, stores and routing rules are created by administrators.
  • The host label of hangar_proxy_upstream_requests_total is the remote's host or a host that matched the repository's related_hosts (or a format's built-in file hosts). It is not capped: a suffix pattern such as .cdn.example.com adds one series per subdomain the remote links to.
  • format, job type and similar values from code or configuration are capped (32 formats, 64 job types); anything beyond becomes other.

Measured on a test node serving three formats, five repositories and a few hundred requests: 666 series in total, 622 of them hangar_*, most of them histogram buckets. Expect low thousands on a busy node with every format in use.

HTTP#

Metric Type Labels Meaning
hangar_http_requests_total counter method, route, code Requests served. A server error (5xx) answered after the client had already gone away (closed the connection, cancelled the request) is recorded as 499, like the 499 handlers answer themselves: nobody read it and the cancellation caused it.
hangar_http_auth_challenges_total counter method, route The 401 answers of hangar_http_requests_total to requests that presented no credentials at all: no Authorization or X-NuGet-ApiKey header, no cookie, and nothing a handler read as credentials from the body. NuGet and .NET clients, docker, npm and pip ask without credentials first and retry with them after this challenge, so it is not a refusal. A 401 to wrong or expired credentials and every 403 are not counted here. sum(rate(hangar_http_requests_total{code="401"}[5m])) - sum(rate(hangar_http_auth_challenges_total[5m])) is the rate of rejected credentials.
hangar_http_request_duration_seconds histogram method, route Time until the handler returned (for downloads, until the last byte was written).
hangar_http_requests_in_flight gauge Requests being served now, including long uploads and the event stream.
hangar_http_request_bytes_total counter route Request body bytes read by handlers.
hangar_http_response_bytes_total counter route Response bytes written.

Package formats#

Recorded for requests served by a format (/repository/{repo}/…, /v2/…) once the addressed repository is resolved. A request through a group is attributed to the group. op is read (GET, HEAD), write (PUT, POST, PATCH), delete or other; repo_type is hosted, proxy or group.

Metric Type Labels Meaning
hangar_format_requests_total counter format, repo_type, op, status_class Package protocol requests; status_class is 2xx … 5xx. A 401 is usually the normal login challenge of docker, npm and pip.
hangar_format_request_duration_seconds histogram format, repo_type, op Package request latency.
hangar_format_upload_bytes_total counter format, repo_type Bytes received in write requests.
hangar_format_download_bytes_total counter format, repo_type Bytes sent in successful (2xx) reads.
hangar_proxy_cache_requests_total counter format, result Proxy requests answered from the cache (hit) or with content a remote supplied (miss), once per client request however many group members were asked. A remote answering not found (or failing) is neither: in a group whose first proxies' remotes do not have a package and whose last proxy serves it from its cache, the request is a hit. Index lookups that only locate a download (a NuGet service index, a cargo, pypi or Helm index) do not count.
hangar_proxy_cache_hit_bytes_total counter format Bytes served from proxy caches without contacting the remote.
hangar_proxy_negative_cache_evictions_total counter repository Remembered remote 404s dropped before their negative_cache_ttl because the repository's negative cache (10,000 paths per remote, least recently used first) was full. A steady rate means clients probe more missing paths than the cache holds, and those probes reach the remote again.
hangar_proxy_index_entries_skipped_total counter format, repository Malformed entries of a remote index (a Helm index.yaml) that a proxy left out instead of failing the whole index, counted each time the index is parsed. A steady rise means the remote publishes broken entries; the warning log line names the first one.

Blob storage#

Operations are timed on the request path (uploads, downloads, publish checks), per driver (fs, s3). Garbage collection accesses stores directly and is measured by the blob.gc job metrics. result is ok, not_found (a normal answer, e.g. a cache miss) or error.

Metric Type Labels Meaning
hangar_blobstore_operations_total counter driver, op, result Operations by op (put, get, stat, delete).
hangar_blobstore_operation_duration_seconds histogram driver, op Latency. put includes streaming the content; get is the time to open the blob.
hangar_blobstore_put_bytes_total counter driver Bytes written before deduplication.
hangar_blobstore_used_bytes gauge store, driver Bytes of live blobs per store (as on the Blob stores screen).
hangar_blobstore_reclaimable_bytes gauge store, driver Bytes of unreferenced blobs that GC frees once their grace period has passed: deleted content, and content that was stored but never published (rejected uploads, digest mismatches).
hangar_blobstore_soft_quota_bytes gauge store, driver Soft quota of stores that have one.
hangar_blobstore_fs_size_bytes gauge store Size of the filesystem holding an fs store, as seen by this node.
hangar_blobstore_fs_free_bytes gauge store Bytes available to Hangar on that filesystem.
hangar_blobstore_usage_age_seconds gauge Age of the usage numbers above.

Store usage is computed every 5 minutes in the background by one aggregate query over the blobs table, so scrapes never wait for it. Until the first run finishes after start the usage gauges are absent.

Proxy remotes#

Metric Type Labels Meaning
hangar_upstream_fetches_total counter format, result Requests to remotes. result: ok, not_modified, not_found, client_error, server_error, circuit_open (refused by the open breaker without contacting the remote), blocked (outbound address policy), canceled, error (connection, TLS, timeout).
hangar_upstream_fetch_duration_seconds histogram format Time to the remote's response headers (fast circuit_open and canceled results are not observed).
hangar_upstream_state gauge repository, state 1 for the current state of each proxy repository's remote on this node: healthy, slow, blocked (401/403 or address policy), offline (the last request failed, or the circuit breaker is open) or unknown (not used since this node started). Refreshed at most every 15 seconds.
hangar_upstream_dns_cache_requests_total counter result Remote host name lookups by DNS cache result: hit, miss (asked the resolver), stale (the resolver failed; the last answer was used), negative (a remembered failure).
hangar_upstream_dns_errors_total counter kind Failed queries to the system resolver for remote host names: timeout, temporary, not_found, other. Retries count. A rising timeout rate points at overloaded DNS servers.
hangar_proxy_upstream_dns_failures_total counter repository Remote requests that failed on a DNS timeout or temporary error. They count towards the circuit breaker at most once per second.
hangar_proxy_upstream_requests_total counter repository, host, result HTTP requests proxy repositories sent to their remote and its related hosts, by final result: 2xx … 5xx, rate_limited (a 429 beyond the Retry-After budget, or the host is still held back after one), error (connection, TLS, timeout, or refused by the outbound address policy), circuit_open (refused by the open breaker without contacting the host) or offline (the repository is in offline mode). A request that was retried counts once, with its last result. Unlike hangar_upstream_fetches_total it names the repository and the host, so it shows which remote, or which download host behind it, fails.
hangar_proxy_upstream_request_duration_seconds histogram repository Time from sending a remote request to its response headers, retries and their waits included. Only requests that got a response are observed (not error, circuit_open, offline or rate_limited results).
hangar_proxy_upstream_retries_total counter repository, reason Retries of remote requests by reason: error (connection failure), 5xx, rate_limited (a 429 within the Retry-After budget). A steady rate means a remote is flaky even when the final results are 2xx.
hangar_proxy_upstream_resumes_total counter repository Interrupted remote downloads continued with a Range request instead of starting over.
hangar_proxy_upstream_inflight_requests gauge repository Remote requests in progress: waiting for a slot, waiting for headers or streaming a body. Requests queued for a slot count too, so with max_concurrent_requests set a value above that limit means requests wait for the remote.

Routing rules#

Routing rules keep internal package names away from proxy remotes and group members (dependency confusion protection).

Metric Type Labels Meaning
hangar_routing_blocked_total counter format, repository, member, rule Package names a routing rule kept from a proxy remote or a group member. repository holds the rule, member is the excluded group member (empty for proxy rules), rule is block, allow (the name was not on a proxy's allow list) or exclusive (another member reserves the name). Every exclusion is counted; it is also logged and audited as routing.blocked, at most once per 10 minutes per node for the same repository, member, rule and package name. A rise for one package name on a proxy means builds asked a public remote for an internal name: either a client is missing the internal repository or someone is probing for a dependency confusion; the audit log names the package.

Logs#

Logs are JSON lines on stderr (log.format: text for development). Every record logged while serving a request carries:

Field Meaning
request_id X-Request-ID of the request: the client's value when it is well-formed (letters, digits, -_., at most 128 characters), otherwise generated; echoed in the response.
trace_id, span_id Current span when tracing is enabled or the client sent a traceparent. Search your trace backend by trace_id.
principal Authenticated user or service account.
repository, format Repository the request addressed (a group, not its member) and its format.

The access log line ("msg":"http request") adds method, path (without the query string), route, status, bytes_in, bytes_out, duration_ms, remote_ip and user_agent. It is written at info, error for 5xx (except 501), and debug for /healthz, /readyz, the metrics path and the web UI's own successful reads: its files and the GET API calls of a browser session (each open tab polls status, events and notifications every few seconds). Writes, failures and requests with a token or from package clients stay at info. Set log.level: debug to see the UI's reads too.

Secrets are never logged. Before a record is written, values of attributes whose name denotes a secret (password, token, secret, authorization, cookie, *_password, *_token, *_secret, …) are replaced with REDACTED, and every message and string value is scrubbed of Hangar tokens (hgr_…), JWTs, Basic/Bearer credentials, passwords in URLs and secret query parameters (token=, password=, X-Amz-Signature=, _state=, …). HTTP headers and query values logged as maps (http.Header, url.Values) have Authorization, Proxy-Authorization, Cookie, Set-Cookie, X-Api-Key and similar entries replaced. A test feeds credentials through every logging path, including the in-memory buffer below, and fails if any of them reaches the output.

System logs screen#

Each node also keeps its newest log.buffer_size records in memory, after the same scrubbing, so administrators can read them under System → Logs without access to the host. The buffer is a fixed ring: appending is constant time and never waits for readers, and the oldest records are overwritten. Warnings and errors are kept longer: the newest of them (a fifth of log.buffer_size, at least 100) stay readable after a burst of info records has overwritten their place. It is lost on restart; full logs stay on stderr, so keep shipping them (docker compose logs hangar, journalctl -u hangar, kubectl logs).

The screen filters by node, minimum level and text, follows new records (refreshing every 5 s, with Pause and Refresh now), opens any line as JSON and downloads the node's buffer, with the current filters, as JSON lines.

The API is GET /api/v1/system/logs (privilege system:cluster:admin):

Parameter Meaning
node Node id from /system/nodes; default the node that answers. Other nodes are asked over HTTP at their server.node_url, signed with the cluster node key.
level Minimum level: debug, info, warn, error.
q Case-insensitive text in the message or attributes.
since RFC 3339 time or a duration back from now (15m).
limit 1 to 5000, default 500.
cursor The cursor of an earlier answer: return only newer records. 0 reads from the oldest record.
wait With cursor, hold the request up to this many seconds until a matching record arrives (long poll, at most 30).
shell
# Follow errors of node hangar-2 from a shell.
c=$(curl -s -H "Authorization: Bearer $TOKEN" "$HANGAR/api/v1/system/logs?node=hangar-2&level=error&limit=1" | jq -r .cursor)
while :; do
  r=$(curl -s -H "Authorization: Bearer $TOKEN" "$HANGAR/api/v1/system/logs?node=hangar-2&level=error&cursor=$c&wait=25")
  echo "$r" | jq -c '.items[]'; c=$(echo "$r" | jq -r .cursor)
done

gap: true in an answer means records after the cursor were overwritten before they were read, or the node restarted. Always pass node when a load balancer spreads requests: a cursor only means something to the node that issued it.

System status screen#

System → Status (privilege system:cluster:read; the sidebar's System entry and the status pill open it) opens with a headline for the whole installation (Everything is working, 1 check needs attention, 2 checks are down, 1 node is not responding), the number of checks passing on the nodes that answer, and the version. Below it, every node has a checklist with one row per subsystem: its state, one sentence and a headline value. Rows that are degraded or down open by themselves; any row opens on click to show its details, what the check probes (database address, blob store path, event bus URL, index name), since when the status holds, the last incident (Was degraded 08:52–10:32), when it was checked and a link to the page that helps (logs of that node, Blob stores, Scheduled tasks, Authentication, Repositories). Under each checklist: host name, scheduler role (the leader schedules tasks; every node executes them), uptime, last heartbeat, the node's own URL and commit. With more than one node, each checklist has the node's name, role and state above it.

Subsystem Headline value Healthy when Degraded when Down when
Database Ping time The readiness ping answers Every pooled connection is in use, or the ping takes over 500 ms The ping fails
Blob storage Least free space of the filesystem stores, else the slowest ping Every store answers its ping A filesystem store has under 10 % and under 5 GiB free A store cannot be opened or reached
Event bus Readiness ping time Listening; job counts readable Job counts unreadable Listener disconnected
Task scheduler leader or follower Task runs can be read A scheduled task is more than an hour late, or runs cannot be read
Search index Probe search time The full-text index is valid and a probe search is fast The index is missing or invalid, or the probe takes over 500 ms The probe fails
Sign-in ok, failing or local OIDC and LDAP worked at their last use (or are not configured) A provider failed; local accounts still sign in
Upstream proxies Slowest smoothed remote latency, or no traffic without requests in the last 5 minutes No proxy remote is offline or blocked A remote is offline or blocked

Since and the last incident come from the node's own observations: since is when the node first saw the current status (at the earliest, its first check after start), and an incident is a period that was not healthy, shown with its worst state once it has ended. Both live in memory, so a restart starts them over.

Each node runs its checks every 15 s (each bounded to 3 s) and writes them to the system_nodes table, so any node can show all of them. A node without a heartbeat for 45 s is shown as not responding (stale, down) with its last report; one silent for an hour is no longer listed, and a node that stops cleanly removes itself at once. The screen refreshes every 15 s; the Live · every 15 s toggle pauses it and the round button refreshes at once. If the database cannot be read, the answering node is shown alone.

The same data is available as JSON: GET /api/v1/system/nodes (every node), GET /api/v1/system/health (the answering node, checked now) and GET /api/v1/nodes (the cluster summary with quorum). The public GET /api/v1/system/status rolls the same checks up into state and message, which every status indicator of the web UI shows; signed-in callers also get the failing checks in problems, with their detail for system:cluster:read.

Traces#

With tracing enabled, Hangar exports these spans over OTLP/HTTP:

Span Kind Attributes
GET /repository/{repo}/* (method + route) server http.request.method, http.route, http.response.status_code, url.path, client.address, user_agent.original, hangar.request_id, hangar.repository, hangar.format, hangar.repository_type, enduser.id
db select, db insert, … db batch, db copy client db.system.name, db.operation.name, db.query.text (parameterised SQL, at most 2 KiB; argument values are never recorded)
blobstore.put / get / stat / delete client hangar.blobstore.driver, hangar.blob.size
upstream.fetch client hangar.repository, hangar.format, http.request.method, hangar.upstream.path, hangar.upstream.result, http.response.status_code
job <type> consumer hangar.job.type, hangar.job.id, hangar.job.attempt

Incoming W3C traceparent/tracestate headers are honoured, so a CI system or reverse proxy that traces requests sees Hangar's spans in the same trace. Hangar does not send trace headers to proxy remotes. Jobs start new traces.

File Answers
hangar-overview.json Is every node ready? How much traffic, how many errors, how slow? Is the database pool saturated?
hangar-formats.json Which formats carry the traffic, fail or are slow? How many bytes go in and out? How well do proxy caches work?
hangar-storage.json How full are the blob stores and their filesystems? Are blob store operations failing or slow?
hangar-upstreams.json Which proxy remotes are offline, blocked or slow? How often do fetches fail and how long do they take? Which repository, and which host behind it, fails, retries or keeps clients waiting?
hangar-jobs.json Is the job queue draining? Which jobs fail or take long? Is every node listening for events?
hangar-auth.json Is someone guessing passwords? Are accounts being locked? Is the audit trail complete? Are routing rules turning away internal package names, and which rules fire?

The dashboards use $__rate_interval, so set the data source's scrape interval in Grafana to match Prometheus.

Alerts#

deploy/observability/prometheus/hangar-alerts.yml:

Alert Severity Fires when
HangarDown critical A node has not been scrapable for 2 minutes.
HangarNotReady critical A node has failed readiness for 5 minutes.
HangarDependencyDown critical A readiness dependency has been down for 2 minutes.
HangarHigh5xxRate critical More than 5% of a node's requests fail with 5xx for 10 minutes.
HangarUpstreamCircuitOpen warning A proxy remote has been offline for 5 minutes while remote fetches on that node failed in the last 15 minutes.
HangarBlobStoreErrors critical More than 5 blob store operations of one kind failed in 10 minutes.
HangarDatabasePoolSaturated warning Over 90% of the pool has been in use for 10 minutes.
HangarJobFailures warning A job failed permanently in the last hour.
HangarJobBacklog warning More than 100 jobs of a type have been queued for 30 minutes.
HangarBlobStoreQuotaNearLimit warning A store has used over 90% of its soft quota for 15 minutes.
HangarBlobStoreDiskNearlyFull critical An fs store's filesystem has had under 10% free for 15 minutes.
HangarStorageUsageStale warning Store usage has not been refreshed for over an hour.
HangarAuthBruteForce warning More than 50 failed authentications in 5 minutes, sustained for 5 minutes.
HangarAccountLockouts warning More than 3 accounts locked in 15 minutes.
HangarAuditEventsDropped critical Any audit event was rejected or lost.

Routing rule exclusions (hangar_routing_blocked_total) and remote retries have dashboards but no alert on purpose: an exclusion is a rule doing its job, and a retry that ends in success needs no one at night. Watch them on hangar-auth.json and hangar-upstreams.json, and read the routing.blocked audit events when a rule fires for a name you do not expect. A remote that stays down is covered by HangarUpstreamCircuitOpen.
