Security

How Hangar protects the artifacts, credentials and accounts it holds, what an operator must configure, and how to report a vulnerability (SECURITY.md).

Threat model (summary)#

Asset Threat Control
Private packages Read or overwrite by a caller without rights Every API operation and package endpoint authorizes the principal (repo:<name>:read/write/delete/admin, system:*); token scopes narrow a user's roles. Enforced twice: at the HTTP boundary and in the services that mutate. Checked end to end by test/security (below).
Accounts Password guessing, credential stuffing, token guessing, account enumeration argon2id hashes, lockout per username and client address with a per-username slow-down (below), the same answer for names with and without an account, per-IP login rate limit, per-IP limit on failed authentications on the API and package endpoints, tokens with 238 bits of entropy and a checksum, stored as SHA-256.
Browser sessions CSRF, XSS, clickjacking, session theft through uploaded content HttpOnly/Secure/SameSite session cookie, CSRF token on mutations, origin check, CORS deny-by-default, CSP for the UI, sandboxed CSP for everything served from package endpoints, X-Frame-Options: DENY, frame-ancestors 'none', nosniff.
Single sign-on Login CSRF, code interception, token substitution, account takeover by name OIDC authorization code flow with PKCE (S256); state, nonce and verifier in a short-lived AES-GCM encrypted HttpOnly cookie (key derived from security.secret_key); ID token signature, issuer, audience, expiry and nonce verified; same-origin post-login redirects only. External identities are linked by issuer and subject and never take over a local, service or other external account. LDAP: filter values escaped, exactly one entry required, empty passwords refused (no anonymous bind).
Upstream credentials and S3 keys Disclosure through a database dump, backup, read-only SQL access or the API Envelope encryption at rest (below); never returned by the API; opened only when the outbound client or the storage driver is built; never sent to redirect targets.
Internal network Server-side request forgery through proxy repositories and README images Outbound address policy: loopback, private, link-local (cloud metadata), CGNAT, multicast, reserved and IPv4-embedding IPv6 ranges are refused when a proxy is saved, on every redirect hop and when a connection is dialled. Only http.allow_private_networks opens exceptions.
Availability Slow-header, slow-body and oversized requests, API floods server.read_header_timeout, body idle timeout, header and API body limits, per-IP API rate limit; uploads are streamed, never buffered.
Rights A limited administrator widening their own rights or taking over an account Grants and account changes are limited to what the caller holds; groups expose only what their creator may read (below). Registry tokens are not credentials: renewing one reloads the account.
Audit trail Repudiation Every mutation, denial and failed sign-in is recorded in the append-only audit log with the client IP (forwarding headers honoured only from server.trusted_proxies).

Out of scope: an attacker who can write to the database or read the server's environment (they hold the secret key, and can redirect a proxy to their own host); a compromised host or reverse proxy.

Privilege escalation model#

Administration is split into privileges (system:users:write, system:tokens:write, repo:<pattern>:admin, ...), so it can be delegated. Delegation never lets a caller go beyond what they hold:

  • Covering. Creating, changing or deleting a role, binding or removing a role, and creating a member with roles need the caller to cover every privilege involved: each one must be implied by one of the caller's own effective privileges (roles narrowed by the token's scopes). repo:team-*:read covers repo:team-a:read; repo:*:admin covers every repository action; two narrower privileges never add up to a wider one.
  • Acting on an account. Setting or resetting a member's password, disabling or enabling, editing, deleting, requiring a password change and ending sessions of another account need system:users:write (or delete) and covering everything that account holds. A helpdesk role with system:users:write can therefore manage accounts without roles, but not a Reader, and never an administrator: only holders of system:* manage holders of system:*.
  • Service-account tokens. system:tokens:write issues a token for a service account only when the caller covers that account's privileges.
  • Passwords set by someone else must be replaced at the next sign-in (must_change_password): the administrator who typed it does not keep a working password of the account.
  • Groups. A group serves its members to everyone who may read the group, so adding a member needs repo:<member>:read for the member and every repository a nested group member reaches; a write member needs repo:<member>:write; turning on anonymous read of a group needs read on everything it reaches. Holders of system:repos:admin may create any repository but are held to the same rule. Routing rules only narrow what members serve. A cross-repository blob mount needs pull on the source, which for a group is the same rule. Every refusal is audited with the repository or privilege the caller lacks.
  • Registry tokens. /v2/token does not treat a registry token as a credential. Presented there, it is renewed only after the account is reloaded from the database (it must exist, be enabled, not be waiting for a password change; a token it came from must still be live and its address restrictions met; roles are the current ones), and the renewed token never expires later than the first token of the chain. There are no refresh tokens (offline_token is ignored, grant_type=refresh_token is refused). A registry token already issued keeps the roles it was issued with until it expires (15 minutes).

Groups created before this rule by someone who could not read a member are not changed; review group members after upgrading (see the changelog).

Sign-in lockout#

  • Failed password checks are counted per (username, client address). After auth.lockout.max_attempts (5) failures within window (15m) that address is locked out of that username for duration (15m) and gets 423 with Retry-After. Other addresses can still sign in, so nobody can lock an administrator out by guessing from their own machine.
  • Failures from all addresses for a username only slow it down: from slowdown_after (10) failures within the window every further attempt waits first, a quarter second doubling up to max_delay (4s). It never locks.
  • Counting is the same for names that have no account, disabled accounts and accounts without a local password, and the answers are the same (401 invalid username or password, then 423). Every refused name spends one password verification's time; a locked-out attempt spends none. Answers therefore do not tell which usernames exist.
  • Wrong current passwords on My account count the same way. A correct password ends the count for that address; Unlock, a password reset and a password change clear it for every address. The members list shows an account as locked while at least one address is locked out of it.
  • The per-IP login rate limit (auth.login_rate) and the failed authentication limit (security.rate_limit.failed_auth) still apply.
  • Once an address has used up its failed-authentication budget, every request from it that carries credentials answers 429 until the budget refills, including requests with a valid token: they are refused before they are checked. Anonymous requests are not affected. CI runners behind one NAT address share the budget, so one job with a wrong or empty token can make the other jobs on that runner fail with 429; fix the job's token, or raise security.rate_limit.failed_auth for such networks.

How secrets and tokens are stored#

Secret Stored as
Local passwords argon2id hash (parameters in auth.argon2), re-hashed on login when parameters change
Personal, service-account and session tokens SHA-256 of the token; the token (hgr_…) is shown once
Proxy upstream password, bearer token, header value Sealed (envelope encryption) in repositories.config
Password in a proxy remote_url or http.proxy URL Sealed in place of the password: http://user:hgs1.…@host
S3 secret key and session token of blob stores Sealed in blob_stores.config (secret_access_key_sealed)
Server-level secrets (storage.s3.secret_access_key, http.proxy_password, docker.token_key, security.secret_key) Not stored; read from the environment

Envelope encryption (internal/secrets). Each value gets a fresh 256-bit data key; the value is encrypted with AES-256-GCM under the data key, and the data key with AES-256-GCM under the key encryption key (security.secret_key). The stored form is hgs1.<key id>.<wrapped data key>.<ciphertext>; the key id is derived from the key, so ids never need to be assigned. Values are sealed when a repository or blob store is saved and opened only by the proxy engine and the S3 driver. The API answers with the password removed and URL passwords as REDACTED; saving the redacted form back keeps the stored secret.

A database check constraint (migration 00050) rejects plaintext secrets in every new or updated row, so no code path can store them by mistake. Rows written before the upgrade are sealed by hangar serve on its first start with a key; until a key is configured they keep working, and the server logs a warning on every start.

Without security.secret_key, creating or updating a repository or blob store that carries a credential answers 501 with an explanation.

Key rotation#

  1. Generate a key: openssl rand -base64 32.
  2. On every node set HANGAR_SECRET_KEY=<new> and HANGAR_SECURITY_PREVIOUS_SECRET_KEYS=<old>; restart the nodes.
  3. Run hangar admin rotate-secrets once (--dry-run shows the counts). It re-wraps every data key under the new key and seals any plaintext left; it exits non-zero if a value cannot be opened with the configured keys.
  4. Remove the old key from previous_secret_keys; restart.

A lost key cannot be recovered: re-enter the affected credentials.

Hardening checklist for operators#

  • Dependency confusion: on every proxy of a public registry, block the names your hosted repositories publish, and reserve them for the hosted member in groups. See guides/routing-rules.md.

  • [ ] Serve Hangar over HTTPS only. Terminate TLS at a reverse proxy, list it in server.trusted_proxies so X-Forwarded-Proto is believed, and set server.base_url to the https:// URL. HSTS is then sent (security.hsts); enable include_subdomains only when every subdomain is HTTPS.

  • [ ] Set HANGAR_SECRET_KEY (and keep a copy in your secret manager) before adding proxy credentials or S3 blob stores. Same value on every node.

  • [ ] Set HANGAR_DOCKER_TOKEN_KEY (32+ random bytes), same on every node.

  • [ ] Single sign-on (guide): keep auth.oidc.client_secret and auth.ldap.bind_password in the environment, use ldaps:// or start_tls (plain ldap:// sends passwords in clear text), never insecure_skip_verify (use ca_file), give the LDAP service account read-only rights, and restrict sign-in with allowed_groups when the provider serves more people than should use Hangar. External sign-ins never take over a local account with the same username.

  • [ ] Keep secrets in the environment or a secret store, never in hangar.yaml (storage.s3.secret_access_key, http.proxy_password, bootstrap.admin_password).

  • [ ] After the first start, remove HANGAR_BOOTSTRAP_ADMIN_PASSWORD from the environment and sign in to change the bootstrap password (Hangar requires it unless bootstrap.require_password_change is false).

  • [ ] Without bootstrap settings, the first start generates the admin password and prints it once to standard error (never into the System logs buffer) and to bootstrap.initial_password_file (mode 0600). Sign in and replace it promptly: until then the account can do nothing else, and the file is deleted after the change. Treat container logs from the first start as sensitive. See first administrator.

  • [ ] In a cluster, a password change or reset takes effect at once on the node that made it, but every other node keeps accepting the old password for up to auth.basic_cache_ttl (default 2m), because each node remembers verified Basic credentials in memory. Disabling or locking an account is not affected: the cached login re-reads the account on every request. When a leaked password must stop working immediately, disable the account until the TTL has passed, or set basic_cache_ttl to a negative value (every Basic request then pays for an argon2 check). Tokens are never cached this way.

  • [ ] Give CI tokens the narrowest scopes (repo:<name>:write) and an expiry; prefer service accounts over personal tokens.

  • [ ] Leave anonymous_read off except for repositories that are meant to be public.

  • [ ] Keep http.allow_private_networks as short as possible: list the internal mirrors by host name or exact CIDR, never whole private ranges. Avoid insecure_skip_verify on remotes; use ca_bundle instead.

  • [ ] Expose only the HTTP port. Do not expose the embedded NATS listener (nats.listen) or PostgreSQL to clients; restrict /metrics at the reverse proxy if it should not be public.

  • [ ] Use TLS to PostgreSQL (sslmode=verify-full) and to S3 when they are on another host; encrypt database backups — they contain password hashes and sealed secrets.

  • [ ] Ship the audit log off the host (export or syslog/webhook) and alert on repeated auth.login.failed and auth.token.failed.

  • [ ] Review security.rate_limit for clients behind one NAT address (all share one budget) and security.limits.upload_body_bytes if uploads should be capped.

  • [ ] Run the container image as shipped (distroless, non-root) and keep it updated.

HTTP hardening reference#

Concern Behaviour Setting
Security headers X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, X-Frame-Options: DENY everywhere; CSP per area: UI (default-src 'self', no inline script), API (default-src 'none', Cache-Control: no-store), package endpoints (sandbox) —
HSTS On HTTPS requests security.hsts.*
CORS Same origin only; preflights and API calls from other origins answer 403 security.cors.allowed_origins
Anonymous API access Only GET /system/status, GET /system/version, GET /auth/providers, POST /auth/login (security: [] in api/openapi.yaml) —
Request headers Bounded; slow headers cut off security.limits.max_header_bytes, server.read_header_timeout
Request bodies API 1 MiB, uploads unlimited and streamed, everything else 64 KiB; a body that stalls is aborted security.limits.*
Rate limits Per client IP (IPv6 per /64): API requests; failed authentications on API and package endpoints security.rate_limit.*, auth.login_rate
Idle connections Closed server.idle_timeout
README images Loaded from Hangar's own origin, see README images; the UI policy keeps img-src 'self' data: unless direct is chosen ui.readme_images, ui.readme_images_allow_http

README images#

Package READMEs reference images on other hosts (badges, logos) and files inside the package or its source repository. The web UI's policy (img-src 'self' data:) blocks other hosts, so the package info API (GET /components/{id}/info) resolves every image of a README and returns, per image source, the URL the browser may load. ui.readme_images decides what that is:

Mode Remote images Privacy
proxy (default) Hangar fetches them and serves them from GET /api/v1/components/{id}/readme-images/{sig} Browsers contact no other host; the image hosts see Hangar's address only
direct Browsers load them from their hosts; the UI policy becomes img-src 'self' data: https: (http: too with ui.readme_images_allow_http) Every image host learns each viewer's IP address, browser, and when a README was opened
off Not loaded; the image's alternative text is shown as a placeholder Nothing leaves the browser or the server

Images stored inside the package (NuGet <icon> and README images in the .nupkg, files in an npm tarball) are always served by Hangar from the stored blob, in every mode. Relative image paths are resolved inside the package first, then in the source repository the package names (github.com and gitlab.com raw file URLs, at the published commit when known).

The image endpoint is not an open proxy:

  • Image URLs are signed with HMAC-SHA256 over the component id and the source; the key is derived from security.secret_key (else generated once and kept in readme_image_key, migration 00160). Only URLs the info API issued are accepted (403 invalid_signature otherwise).
  • The caller needs read access to the component's repository, like for the README itself (401 signed out, 404 without access).
  • Fetches use the outbound HTTP settings (platform default proxy, CA bundle) and the outbound address policy on the URL, on every redirect hop (at most 5) and on every dialled address. https only: http:// sources are upgraded to https:// and redirects to http:// refused, unless ui.readme_images_allow_http. No cookies, credentials or referrer are sent; 15 s and 5 MiB at most.
  • Only content that sniffs as PNG, JPEG, GIF, WebP, AVIF or SVG is served, whatever type the remote declares. Responses carry Content-Security-Policy: default-src 'none'; style-src 'unsafe-inline'; frame-ancestors 'none'; sandbox, X-Content-Type-Options: nosniff and Cross-Origin-Resource-Policy: same-origin, so an SVG opened on its own runs no script and loads nothing.
  • Results are cached in memory (32 MiB) and in readme_image_cache for 24 hours, failures for 15 minutes, shared by every node. A remote image that cannot be loaded answers 404 image_unavailable (not a 5xx, so a broken third-party badge does not trigger server error alerts).

Security tests#

test/security runs against a real hangar serve (it needs HANGAR_TEST_DATABASE_URL, as in CI):

  • Authorization sweep: every operation in api/openapi.yaml and every package endpoint of every format is called as an anonymous caller, as a reader and with a token scoped to other repositories, against private hosted repositories and a group and a proxy over them. Any answer that serves a caller who must be refused fails the build. An API operation or format route that is not classified in the test fails it too.
  • Privilege escalation through tokens, roles and the registry token service; group membership escalation (a repository administrator cannot expose a repository they cannot read); a helpdesk role cannot take over an administrator; a disabled user cannot renew a registry token.
  • SSRF: remotes at loopback, 169.254.169.254, private and IPv6-mapped addresses are refused; rows that bypass that check are blocked when fetched; redirects to internal addresses or other schemes are not followed.
  • Upstream credentials: stored sealed, never returned, sent only to the remote, not to redirect targets.
  • Headers, CORS and size limits on the running server.
